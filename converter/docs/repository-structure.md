# Repository structure

The converter has two parts: the **tooling** in `converter/` (agents, rules,
contracts, tools, shared packages), and one **converted application per
project** in `projects/<Project>/converted/`, next to that project's
`INPUTS/` and `OUTPUT/`. The layout has to stay navigable at 1 project and
at 20, so it follows four rules:

1. **One converted application per project**, in
   `projects/<Project>/converted/`. A converted app never imports from
   another project's app.
2. **Code is organised by business capability**, not by OutSystems module.
   OutSystems splits code into technical layers (`_CS`, `_IS`, `_MUI`, `_MCW`,
   `_MTH`, …). Copying those names would recreate the platform's
   architecture canvas in C#/TypeScript. Each capability gets one module per
   component (backend domain, web feature, mobile feature), and the app's
   `module-map.md` records which OutSystems modules feed it.
3. **Shared code only goes in `converter/packages/` when a second app needs
   it.** Until then it lives in the app. This avoids shared libraries
   designed around guesses.
4. **os2native's output stays in `projects/<Project>/OUTPUT/`.** The
   converted app cites it by path and run id and never copies it.

`projects/` is git-ignored in the root repository, so `converted/` is **not
versioned there**, by the user's decision. Never stage or commit it through
the root repository. If an app needs version control of its own, propose a
separate repository inside `converted/` and create it only with the user's
approval.

## Layout

```text
converter/                        # tooling, shared by every project
├── README.md                     # what the converter is and how work flows into it
├── AGENTS.md                     # stage 5 flow, converter manager, hard rules
├── CONVERTER_AGENT.md            # global rules for the BA, ARCHITECT, DEV and QA agents
├── agents/                       # role guides: Starter, BA, Architect, Dev, QA
├── contracts/
│   └── os2native-intake-contract.md   # what os2native must deliver per project
├── tools/
│   └── intake_check.py           # automated intake gate (stdlib Python)
├── docs/                         # this file, conventions
└── packages/                     # code shared by ≥2 converted apps (empty until needed)

projects/<Project>/
├── INPUTS/  OUTPUT/  project.json  # the extractor's side (read only for the converter)
└── converted/                    # the converted application (written by the converter)
    ├── README.md                 # source package and run id, target stack, status, how to run
    ├── module-map.md             # OutSystems app/module → target component/capability
    ├── intake/
    │   ├── intake-check.md       # generated by converter/tools/intake_check.py
    │   └── intake-review.md      # manager's review, os2native change requests, hand-off conditions
    ├── project-documents/        # sources.md (links + run id), iterations.md, user_stories.md, architecture.md, handoff.md
    ├── backend/                  # API + scheduled jobs
    ├── db/                       # migrations and seed data
    ├── web/                      # web front-end(s), one folder per OutSystems web app if more than one
    ├── mobile/                   # mobile app
    └── qa/                       # QA case register and timestamped run results
```

Create a component folder only when development of that component starts.
Don't add empty placeholders.

## Inside each component (default stack)

The default stack is [`../../TECH_STACK.md`](../../TECH_STACK.md): an ASP.NET
Core (.NET 10) back end, or Node.js + TypeScript when the project chose
`node` (`"stack"` in `projects/<Project>/project.json`, repeated in the
handover's Decisions), PostgreSQL, React + Vite for web and React Native
(Expo) for mobile. If an app's README names a different stack, the Architect
confirms which one applies before development. Whatever the stack, keep the
same shape: capability modules, a thin shared core, and integrations behind
interfaces.

### `backend/` (.NET 10, modular monolith)

```text
backend/
├── src/
│   ├── Api/                      # ASP.NET Core host: endpoints, auth, OpenAPI document
│   ├── Worker/                   # timers and BPT replacements (Hangfire or SQS consumer)
│   ├── Modules/
│   │   └── <Capability>/         # one folder or project per capability
│   │       ├── Endpoints.cs      #   transport only (Minimal APIs or controllers)
│   │       ├── <Capability>Service.cs   # business rules (cite BR ids in comments/tests)
│   │       └── Data/             #   EF Core entities and queries; Dapper for ported Advanced SQL
│   ├── Integrations/
│   │   └── <System>/             # one Refit client per external system (was an *_IS module)
│   └── Platform/                 # config, auth, audit, logging, DbContext, crypto
└── tests/
```

With `node`, the same shape under `backend/src/`: `api/`, `worker/`,
`modules/<capability>/`, `integrations/<system>/`, `platform/`.

Dependency direction: `Api`/`Worker` → `Modules/<Capability>` →
`Integrations` (through interfaces declared by the capability) and
`Platform`. Capabilities don't use each other's internals; they call each
other's public service interface or communicate through events.

### `db/`

```text
db/
├── migrations/               # numbered, forward-only; first one built from deliverables/db-schema/schema.sql
└── seeds/                    # static entities (from seed-data.sql), never customer data
```

### `web/` (React + TypeScript + Vite)

```text
web/<web-app>/src/
├── routes/                   # routes only (one route per OutSystems screen in scope)
├── features/<capability>/    # components, TanStack Query hooks, forms (react-hook-form + zod)
└── shared/                   # design tokens, layout, UI primitives (shadcn/ui), generated API client
```

### `mobile/` (React Native, Expo)

```text
mobile/
├── app/                      # Expo Router routes (one per OutSystems mobile screen in scope)
└── src/
    ├── core/                 # theme (from *_MTH), patterns (from *_MPat), local DB (expo-sqlite, from *_MDB), sync, network
    └── features/<capability>/ # screens, components, hooks, local tables
```

## Naming

- Folder and package names: `kebab-case` for folders outside code, the
  language's convention inside code (`PascalCase` C# projects and namespaces,
  `kebab-case` or `camelCase` TypeScript files as the project settles).
- Capability names come from the product spec's feature names, not OutSystems
  module names (`bookings`, not `booking_is`). Integration clients are
  named after the external system (`integrations/payment-gateway`).
- Traceability: stories, tests and PR descriptions cite spec IDs (`F8`, `BR26`, `J3`)
  and the iteration (`I2`).

## Adding a new converted application

1. The extractor (os2native) takes the project through stages 1–4
   ([`../../STAGES.md`](../../STAGES.md)): extraction, verification approved
   by the user, product spec and prototype in `OUTPUT/SPECS/<App>/`, and
   `OUTPUT/SPECS/CONVERTER_HANDOVER.md` approved by the user.
2. Run `tools/intake_check.py`, check the handover and verification
   approvals (contract §6), then write `projects/<Project>/converted/intake/intake-review.md`.
3. When the gate passes, STARTER creates `projects/<Project>/converted/README.md`,
   `module-map.md` (from the handover's capability map) and
   `project-documents/` (`sources.md`, `iterations.md`, `handoff.md`).
4. Run the conversion loop per iteration (BA → ARCHITECT → DEV → QA → user
   acceptance), as described in [`../AGENTS.md`](../AGENTS.md).
5. When code would be copied from another app, move it to `packages/` instead.
